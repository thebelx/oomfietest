oomfie — an unbounded stack write in sys_ipmimgr

bel · jb.0d01.wtf

PS4 13.02's IPMI manager — sys_ipmimgr, syscall 622 — has a stack buffer overflow in the create-server handler. The function walks the pending-connect list and writes two uint32 values per matching entry into two adjacent 256-byte stack arrays, with no bounds check on the write index. The list has no length cap. With 64 or more queued connect requests, the writes overflow; with 79 or more, the stack canary trips.

The overflow is only the surface. The values written come from the pending-connect entries themselves — the (server_id, uid) pair that serves as the identity key for ConnectRequest objects. That pair is propagated by the same function into freshly- allocated ConnectRequest structures. Two objects can end up claiming the same identity, and the free path for ConnectRequest is unguarded. That's where the exploit lives: an identity collision that leads to a use-after-free.

Before you run the PoC. The static analysis below is verified against the 13.02 kernel dump. The trigger sequence has not been executed on hardware. The PoC's argument block layout, its command numbers, and its return-value handling are reconstructions from the disassembly — they may not match the actual userspace ABI. On a real console it may fail at the first call, return EINVAL for every command, or panic the kernel. Run it on a console you are prepared to lose.

The finding does not depend on the PoC working. The disassembly is the evidence.

The vulnerable function

syscallCreateServer (FUN_00efb220) builds a server structure and then iterates the pending-connect list. Its stack frame, from the disassembly of the loop body: 

array_A   at RBP-0x170, 64 × uint32 = 256 bytes   — ends at RBP-0x70
array_B   at RBP-0x270, 64 × uint32 = 256 bytes   — ends at RBP-0x170
local_78  at RBP-0x78, 32 bytes   — internal copy of the server name
local_58  at RBP-0x58, 24 bytes   — user-supplied name copy
local_40  at RBP-0x40, 1 byte     — null terminator
canary    at RBP-0x38, 8 bytes

The two arrays are physically adjacent: array_B ends exactly where array_A begins.

The trigger — no length cap on the pending list

The list is at server_list + 0x38, a global. Entries are appended by FUN_00ef10d0 (cmd 0x400). The append path:

    if ((*(int *)(puVar2 + 3) == param_2) &&
        (*(int *)((long)puVar2 + 0x1c) == uid)) {
        FUN_00ae0450("...ERROR...", 0x44f);   // panic on duplicate
    }

// link new entry in
*(byte *)((long)puVar14 + 0x14) = *(byte *)((long)puVar14 + 0x14) | 1;
*puVar14 = 0;
puVar14[1] = *(undefined8 *)(server_list + 0x40);

The duplicate check panics only if both the server-id field (+0x18 of the entry) and the uid field (+0x1c) match an existing entry. Varying the server id bypasses it. The counter at +0x34 increments but is never compared to a maximum.

The list has no upper bound. Its only limit is available kernel memory.

No privilege gate

The dispatcher FUN_00f061d0 has a credential check at the top: 

if (iVar5 < 0x271) {
    uVar14 = iVar5 - 0x100;
    if (uVar14 < 0x34) {
        // cred check for cmds 0x100..0x133
    }
}
else if ((((iVar5 == 0x271) || (iVar5 == 0x372)) || (iVar5 == 0x473)) &&
        (...)) {
    // cred check for those three
}

cmd=0 sets iVar5 = 0. Condition iVar5 < 0x271 is true; uVar14 = 0 - 0x100 = 0xFFFFFF00, not < 0x34. Skipped.

cmd=0x400 sets iVar5 = 1024 > 625. The else if requires 0x271, 0x372, or 0x473. Not matched. Skipped.

Both commands bypass the credential check. The only remaining gate is the top-level in_size ≤ 0x40 bound applied to all commands.

From stack overflow to use-after-free

The interesting thing about the overflow is not that it writes past an array. It's what it writes, and where those values end up.

What the values are

Both values written per iteration come from the pending-connect entry: 

plVar13[3]                            → the "server id" field of the entry
*(undefined4 *)((long)plVar13 + 0x1c) → the "uid" field of the entry

These are the same two fields the connect-path lookup uses as its compound key. They are the identity of the ConnectRequest.

Where they go next

Immediately after the overflow loop, a second loop reads the arrays back and writes their contents into freshly-allocated ConnectRequests: 

uVar12 = 0;
do {
    lVar8 = FUN_00ef74d0();                       // allocate ConnectRequest
    if (lVar8 == 0) { ... panic ... }
    *(undefined4 *)(lVar8 + 0x10) = 0x40;
    *(undefined4 *)(lVar8 + 0x18) = auStack_A[uVar12];   // server id
    *(undefined4 *)(lVar8 + 0x1c) = auStack_B[uVar12];   // uid
    FUN_00ef7f10(local_288, lVar8);               // link into server's list
    uVar12 = uVar12 + 1;
} while (uVar11 != uVar12);

FUN_00ef74d0 allocates from the SceIpmiMgrConnectRequest zone (confirmed: the function loads its zone pointer from a single global, DAT_02f7d630, which is populated at module init).

For uVar12 < 64, the array values still hold the correct identity for that entry. For uVar12 ≥ 64, the array slots have been clobbered by the other array's write, and the ConnectRequest gets assigned a different entry's identity.

The free is unguarded

The free counterpart is FUN_00ef74b0: 

void FUN_00ef74b0(void *obj) {
    FUN_00a111b0(_DAT_02f7d630, obj, 0);      // uma_zfree, nothing else
}

No unlink from the list. No reference count. No state check. The caller is entirely responsible for ensuring the object is unreferenced and unlinked before freeing. Twenty call sites across the module, and every one of them assumes that precondition holds.

The resulting UAF

Two ConnectRequests on the list now claim the same (server_id, uid) identity. The next time any caller resolves that identity — a connect, a lookup, a disconnect, a session teardown — the walk returns the first matching node, which may not be the one the caller owns. Depending on what the caller does next:

  • Free the wrong object. Caller A frees what it thinks is its ConnectRequest, but the lookup matched B. B is now freed while still linked into C's list. C's next walk dereferences freed memory.
  • Double-free. Both A and C later free the object. The second free is a double-free of a UMA object.
  • State confusion. A writes a field on the "shared" object, which C reads as a genuine update. Sessions can be hijacked or destroyed by a process that didn't own them.

Which of these three fires depends on which operation the caller performs after the corrupted ConnectRequest is inserted. The eight internal callers of FUN_00ef74b0 are the candidates: FUN_00ef10e4, FUN_00ef4260, FUN_00efa000, FUN_00efc840, FUN_00f013f0, FUN_00f030a0, FUN_00f04840, FUN_00f08de0, FUN_00f0a720.

The PoC

Again: this has not been tested. The argument block layout, the command numbers, and the sequence are reconstructions from the disassembly. The exact userspace ABI of sys_ipmimgr — how the kernel expects the argument block to be shaped, what the server name field actually contains, whether the connect handler accepts the arguments as written — is not confirmed against a running system. On a retail console it may return EINVAL for every call. On a devkit it might do something else. Run it on a console you can afford to lose, ideally with UART attached so a panic is visible.

If it does reach the vulnerable path, the conservative setting N_REQUESTS = 72 corrupts the neighboring stack locals without touching the canary. N_REQUESTS = 78 is the last safe value. Anything at or above 79 trips the canary and panics the kernel.

The PoC has seven phases: baseline, queueing, trigger, identity collision stress, server teardown, post-teardown observation, and summary. Phases 1–3 are based on verified disassembly. Phases 4–6 are speculative — they attempt to consume the corrupted state, but their exact design is inferred rather than traced.

Download ipmi_poc.js

The script is designed for the chain_poops environment — WebKit primitive already established, JavaScript issuing syscalls via the ROP harness. It will not run from a plain browser page or any sandboxed context. A companion C PoC for a devkit or payload SDK is planned but not yet written.

How to run it

Load it as ipmi_poc.html with the primitive harness in place. URL parameters override the defaults: 

?n=72              queue 72, trigger, full phase 4-6
?n=72&phase4=0     skip the collision stress
?n=72&phase5=0     skip the teardown
?n=78              last safe value — expect no panic
?n=79              canary trip — expect reboot

Run ?n=63 first as a control — that should complete all phases without a reboot. Then ?n=72, then ?n=79. If the console reboots at ?n=72, the UAF fired from phase 4 or 5. If it completes cleanly, the collision didn't happen under those parameters.

Open questions

  1. Which caller of FUN_00ef74b0 resolves identity before freeing. The UAF requires a caller that looks up a ConnectRequest by (server_id, uid) and then frees it. Any of the eight internal callers is a candidate; tracing their lookup paths finds the exact trigger.
  2. Whether the second loop's allocation can be groomed. The SceIpmiMgrConnectRequest zone is only reachable via the connect path. If it's a fixed-size zone, the freelist is predictable; if it's a malloc-backed zone, the slab geometry matters.
  3. Whether the primitive can be chained. The UAF is on a ConnectRequest. What gets allocated into the freed slot determines whether the primitive is consumable. A second syscall that allocates a function-pointer-bearing object in the same zone would be ideal.
  4. Whether cmd=0 is genuinely unrestricted on retail. The dispatcher's check skips it, but a higher layer (SceShellCore, the syscall wrapper, a separate credential validator) might intercept it. The static analysis says no gate; a live test would confirm.

Relationship to other findings

This is a separate finding from Fahrenheit, which covers a UFS mount path superblock-validation issue on the same firmware. The two share one property: both are kernel-side bugs on 13.02, and both require a userspace primitive to be exploited end-to-end. The difference is that Fahrenheit needs a 250 GB USB 3.0 drive to trigger the mount path, while this one needs two syscalls and nothing else.

There is also no working userspace primitive on 13.02 for either finding. The WebKit SSV exploit that would have provided one does not fire on this firmware — the JavaScriptCore deserializer's object map was rebased and no longer overflows. That gap is common to both findings and is not solved by either.
