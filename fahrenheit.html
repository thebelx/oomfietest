Fahrenheit — unvalidated UFS superblocks on 13.02

bel · jb.0d01.wtf

The UFS mount path on 13.02 accepts superblocks that its own validator would reject. The 13.52 validator is fail-open: it runs, its return value is discarded, and execution continues with the unvalidated superblock. On 13.02 the validator call is absent entirely. Both firmwares mount crafted superblocks. The downstream write loop derives its length from fields the arithmetic never bounds-checks. The multiplication wraps.

What follows is the diff, the arithmetic, the reachability analysis, and — importantly — the three gaps that keep this from being a jailbreak route. The finding is real. The exploitation path is not complete, and one of the missing pieces is a piece of hardware I don't currently have.

The two functions

Both firmwares have ffs_mountfs as the UFS filesystem mount entry point. On 13.52 it's at kernel base 0xffffffff80000000 + 0x4e9640 (FUN_ffffffff824e9640). On 13.02 it's at the same relative position in a different binary (FUN_00ae9510, base 0 in the dump).

The validator runs. Its return value is logged and discarded. Execution proceeds down the "assume valid" path. This is fail-open: the check is present but ineffective.

No validator call. The mount path proceeds if five conditions hold. The effect is identical to 13.52.

The five 13.02 conditions are:

  1. fs_magic == 0x19540119 (UFS2)
  2. fs_sbsize == expected_for_this_iteration
  3. fs_bsize <= 0x10000
  4. fs_bsize >= 0x560
  5. field_0x528 >= 1

Every operand is int or uint. The multiply fs_ncg * 4, the two adds, and the assignment to local_5c all happen in 32-bit.

(ulong) casts on fs_ncg before the multiply, (long) cast on field_0x9c. The whole expression is evaluated in 64-bit. 5 * fs_ncg cannot wrap for any 32-bit fs_ncg value.

That's the patch. Sony widened the arithmetic on 13.52. On 13.02 it still wraps.

Loop count: ceil(field_0x9c / fs_fsize / fs_frag). Per-iteration write: fs_bsize. Total bytes written: N * fs_bsize.

In a well-formed superblock, fs_bsize == fs_fsize * fs_frag and field_0x9c is a multiple of fs_bsize. The write fits inside the allocation exactly.

In a crafted superblock where the relationship is violated — for example,

That's a pile driver, not a clean overflow. Exploitation wants a tighter overrun. The quantity to control is: 

overrun = N * fs_bsize - (field_0x9c + 5 * fs_ncg)

Reachability: the six paths to ffs_mountfs

ffs_mountfs is not called directly. It sits behind ffs_mount in the ffs_vfsops table. There are six plausible delivery paths.

1. USB automounter — the intended target undetermined

SceAutoMounterIpc handles device arrival events. On insert, it probes the device for recognizable filesystems and calls nmount(2) with the fstype it detects. If "ufs" or "ffs" is in the probe list, a crafted USB drive reaches ffs_mountfs.

Public Celsius research confirms this is the intended trigger: the exploit requires a USB 3.0 drive of 250 GB or larger, connected via the console's external storage feature. The automounter does probe the device for filesystems.

The LVD query inside ffs_mountfs fails gracefully (returns -1 through local_8c) rather than aborting. That branch exists specifically to handle a UFS mount where LVD isn't present, which is the USB case.

2. Direct nmount(2) from userspace privileged

If vfs.usermount is enabled, an unprivileged process can call nmount(2) with an arbitrary fstype. Even if enabled, nmount requires a device vnode for the target filesystem. A browser sandbox typically cannot open /dev/da0 directly.

3. Boot-time mountroot not runtime

vfs_mountroot.c exists in the binary. If UFS is the root fstype on any configuration, the mount happens at kernel init. You cannot deliver a crafted drive across a power cycle, so this path is not usable.

4. Internal LVD HDD mount requires prior jailbreak

The internal HDD is mounted as UFS2 at boot. Writing to the raw partition requires root-equivalent privileges. Chicken and egg.

5. BD-J triggered mount hardware

If a BD-J application can invoke a syscall that reaches vfs_mount, it may be able to mount a UFS filesystem from a disc. Requires a Blu-ray burner, the BD-J exploit, and confirmation that the BD-J syscall surface exposes mount(2).

6. Firmware update path no

Sony's update mechanism parses PUP files, not UFS superblocks. Not relevant.

Testing USB reachability requires hardware I don't have. The constraints, as far as they can be established from public documentation and the Celsius research:

I have none of these. The cheapest path is a used USB 3.0 250 GB drive (~$30) paired with a UART adapter (~$10) on a second console. That's still $40 plus the risk of damaging the console during soldering, plus the cost of a console I'm willing to lose.

There is a partial workaround: a USB 3.0-capable device emulator could present itself as a 250 GB+ USB 3.0 drive while logging the SCSI commands the PS4 sends. A Raspberry Pi Zero 2 W ($15) can do this, but it's USB 2.0 only, so if the automounter checks the negotiated link speed rather than the descriptor version, the Pi won't be probed either. The check is probably at the driver level, not the descriptor level — the console reports a specific error for USB 2.0 devices — which means the Pi is out.

A USB 3.0-capable gadget device is more expensive: a Raspberry Pi CM4/CM5 with a USB 3.0 carrier board is $70–120, an NXP i.MX8 board is $200+, a Total Phase USB 5000 is $1500+. None of these is currently available to me.

What the missing test would establish

The USB test resolves one question: is ffs_mountfs reachable from external media on 13.02?

Three outcomes:

  1. Automounter probes UFS, kernel panics. Fahrenheit is confirmed reachable. The finding moves from "verified vulnerability" to "verified reachable vulnerability." This is the good outcome.
  2. Automounter probes UFS, no panic. Either the write landed harmless, or the mount path rejected the image before the write loop. Tunable. The finding is confirmed reachable but the trigger needs refinement.
  3. Automounter does not probe UFS. Fahrenheit is HDD-only, which means it requires a prior jailbreak to trigger, which makes it circular. The finding remains real but useless as an initial exploit.

All three outcomes are publishable. Outcomes 1 and 2 strengthen the finding. Outcome 3 narrows its scope. None of them are conclusions I can reach without spending money on hardware.

The wall

Even a confirmed overflow doesn't give you a jailbreak. Three things are required for a kernel bug to become a working primitive:

  1. A userspace entry point that runs code inside the browser sandbox and can reach the mount subsystem.
  2. Heap shaping before the bug fires, in the exact UMA zone the summary buffer allocates from.
  3. A way to consume the corrupted state after, without the kernel detecting it and panicking.

On 13.02 there is no public userspace primitive. The WebKit SSV exploit that slopkit provides does not fire on this firmware. The MemoryMap has been rebased to a HashMap in Safari 17, and duplicate reference identity is preserved correctly.

Even with a userspace primitive, the heap shaping problem remains. The UMA zone that ffs_mountfs allocates from is not reachable from any syscall. Shaping it requires a second kernel bug.

The kernel finding is real. Two of the three prerequisites for exploitation are missing, and one of the three is behind a hardware paywall I can't currently clear.

What Fahrenheit is, finally

Fahrenheit is a verified kernel vulnerability on PS4 13.02. It is reachable from the mount subsystem under conditions that require hardware to determine. It is not exploitable without a userspace primitive and a kernel heap shaping primitive, neither of which currently exists on this firmware.

Its value is threefold:

  1. As a reference finding. The 13.02/13.52 diff shows Sony widening the allocation arithmetic between those firmwares, which is a data point about their patch cadence on the UFS subsystem.
  2. As a component. If a userspace primitive ever appears on 13.02, Fahrenheit is one of the pieces you can chain. The hardware gate on the USB test is the only thing blocking confirmation of the trigger.
  3. As documentation. The ffs_mountfs path on 13.02 is now analysed. Anyone attempting a UFS-based exploit doesn't need to redo this work.

It is not a jailbreak. It was never going to be, on its own.
